# Ciphertext encoding leaves the six unused accumulator bits at zero (distinguisher)

**Affected:** `kemeleon` 0.1.0-rc.1 (latest crates.io release), `main` at `cb139f8`. ML-KEM-768 confirmed; ML-KEM-512/1024 use the same code path (`MSB_BITMASK` 0b1100_0000 / 0b1110_0000).

## Summary

In the current draft (draft-irtf-cfrg-kemeleon-02, July 2026), `EncodeCtxtR` calls `VectorEncodeR`, which ends with `IntegerRandomizeUnused`, and `DecodeCtxtR` calls `VectorDecodeR`, which begins with `IntegerClearUnused`. Earlier revisions (draft-veitch-kemeleon-00, draft-irtf-cfrg-kemeleon-00 and -01) did not have these steps, and the crate (December 2024) predates them, so this is a report against the current revision rather than a claim that the crate departed from the text it was written against. The crate does this for encapsulation keys (`encapsulation_key.rs`, `encode_priv` / `decode_priv`) but not for ciphertexts:

* `kemeleon/ciphertext.rs`, `Ciphertext::encode`: after `vector_encode`, the top byte `dst[T_HAT_LEN - 1]` keeps the unused bits at zero; no random bits are OR-ed in.
* `Ciphertext::decode`: `vector_decode` is called on `c1` without clearing the unused bits first.

## Impact

Every encoded ciphertext has six fixed zero bits at a known offset (byte 1123, mask `0xFC` for ML-KEM-768). A test on those bits detects every ciphertext produced by the crate, with a false-positive rate of 2^-6 on uniform input (2^-12 for the two ciphertexts of a pq-obfs handshake). That is a stronger distinguisher than the compression bias (≈67% recall per raw ciphertext at α = 10^-3) that the ciphertext encoding is meant to remove. Encode/decode round trips and interoperability tests do not reveal it.

Because the decoder does not clear the bits, it also rejects conforming ciphertexts from other implementations unless the six random bits happen to be zero (we observed 4/200 accepted, against 3.1 expected).

## Reproduction

```
cargo run --release --example interop -- gen 1000 > v.json
python3 -c "import json;b=[bytes.fromhex(json.loads(l)['ct_kmln'])[1123]&0xFC for l in open('v.json')];print(sum(x==0 for x in b),'of',len(b))"
# -> 1000 of 1000   (encapsulation keys, field ek_kmln: about 1 in 64, as expected)
```

## Test vectors

`kemeleon768_decode_vectors.json` (attached; generated by an independent Go implementation) holds 520 decoding vectors for ML-KEM-768: for keys and ciphertexts of the rejection encoding, four base objects with each of the 64 values of the unused bits, plus default-encoded objects. Each vector gives the representative and the raw FIPS 203 object it must decode to. The crate decodes only 4 of the 256 rejection-encoded ciphertext vectors: exactly those whose unused bits are zero.

## Suggested fix

In `Ciphertext::encode`, after a successful `vector_encode`, draw one byte from the rng and set
`dst[T_HAT_LEN - 1] |= r & MSB_BITMASK`; in `Ciphertext::decode`, clear
`c1[T_HAT_LEN - 1] &= MSB_BITMASK_INV` before `vector_decode`. A test like the existing
`bit_entropy_check` for keys, applied to ciphertexts, would catch regressions; published test vectors that pin the unused-bit handling would help other implementations.

Found by differential testing for the paper "Migrating a Deployed Censorship-Circumvention Transport to Post-Quantum Key Exchange" (under submission). Happy to send a PR.
